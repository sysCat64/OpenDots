## 6. Differences, interpretations and ambiguities (none required stopping)

The instruction was to stop if the documents did not specify something necessary to reconstruct **safely**. These points are where the documents were silent or ambiguous; each was resolved from the documents' own stated requirement, and none was invented from the lost code. I flag them so they can be challenged.

1. **Interlock condition.** P2a-4 section 13 says both "refuses an input that leaves out a tool result the durable log holds" and "the history handed to the agent never contains an unresolved server tool call whose result the log already holds". The rebuild implements the second: refuse an input whose history contains an assistant tool call without its tool message **while the log holds a `TOOL_CALL_RESULT` for that call**. Read literally against _every_ result in the log, the first reading would refuse every prompt-only headless turn (the P3 contract) on any thread with tool history. Still **provisional**, as the originals say.
2. **Classification residue.** The table covers "tool call resolved or pending" and "complete text with no tool call". A run with a tool call whose result is durable and **no terminal** is recovered with `RUN_ERROR` only (P2a-4 Case C); a complete text message **without** any tool call is deferred (R26). The table does not say what to do with a resolved tool call followed by a **complete** continuation text and no terminal; the rebuild treats it as Case C.
3. **Run status for an in-process abnormal end** is `error`; `stopped` for a stop (section 8.1); `interrupted` is reserved for recovery. The documents do not name the in-process abnormal-end value.
4. **Transaction grouping under W1** is inferred from the arithmetic the P2a-7 and R32 documents give (1,500 transactions per 100 turns = 14 events + 1 cache write per turn): one transaction per streamed event; a terminal event and its status update together; finalizer closers and status together; recovery in one transaction; the cache write separate. Reproduced: G0 is 11.
5. **Cache check order.** The R32 table says a truncated payload is a **hash mismatch**. My first version parsed before hashing and reported `malformed`; the corruption control exposed it and it was corrected (hash first; `malformed` means a matching hash over a non-array). A genuine rebuild finding, fixed.
6. **`ready()` and `listThreads` details** (`checked` counts threads; the healthy check compares payload, hash, checkpoint and last event id; a thread is listed once it has a non-`running` run) are inferred from the `{checked, rebuilt}` observations and the "not listed while `running`, listed after recovery" statements.
7. **Fake provider and the harness are my own design** (marker-driven; chunk text `chunk-NN ` and `gNN `; shorter chunk delays than the original 150 ms; T1 holds a `chunk-NN` stream rather than a `gNN` one). The documented shapes, counts and assertions are what matter and they reproduce.
8. **Capture / snapshot structure** is mine. It follows the documented key places (for example the five G3 divergence places: `runs[0].clientEvents[0]`, `runs[0].runnerEvents[0]`, `snapshot.compactedEvents[5]`, `snapshot.http.events.body.events[5]`, `snapshot.replay[5]`), which my fixtures reproduce exactly.
9. **All cache columns are created at once** on a fresh database (no `ALTER TABLE` migration from an earlier phase); the migration path was not rebuilt.
10. `DotAgent` is the real one with a non-empty dummy `intelligenceKey`, the documented trick. **It means the rebuilt candidate still carries a dummy Intelligence key in `PlatformConfig`**; this is a P5 concern (see the P5 note in section 12).

## 10. Host instability (R33) and non-reproducible failures: recorded, not hidden

On this machine **106 node crash reports had accumulated before today's tests (earlier days included) and 28 more appeared during them** (about 18:45 to 19:30): `SIGSEGV` and `SIGTRAP` inside V8 (concurrent GC marking, `MarkCompactCollector`, the Maglev / Turboshaft compiler workers, `HeapObject::SizeFromMap`, `Abort()`), on both worker threads and the main thread. This is the documented **R33** (cause unknown, not attributed to Node 24 or macOS 12). It is **not** a runner defect and it is **not** a semantic regression.

Consequences, all recorded:

- My first harness did not recognise a child killed by a signal (`exitCode` is `null`), so the first such crash showed up as a **60-second timeout in the P2a-3 T3 test**. That was a defect in my harness; it now classifies the death immediately and says so.
- Mitigations (the R33 rules from the documents): V8 `--single-threaded` in child processes; a role that dies **before it started** (before any write) is restarted, bounded; a role that dies **after** it started is never silently retried; a typed `HostInstabilityError` is the only thing that may re-run a whole test, assertion failures never are; incomplete vitest runs are re-run and every attempt is recorded. The harness recorded **14 child-process deaths** (10 before start and restarted; 4 after start), 8 distinct roles, 9 `SIGSEGV` and 5 `SIGTRAP`; records are in `rebuild-evidence/local-first/host-instability/`.
- Two vitest processes were themselves killed by the host (V2 attempt 1 reported 105 tests; an earlier V2 run reported 0 in 2 s; an earlier V4 reported 100 of 118). They were re-run; the incomplete attempts are kept in `regression-first-attempt-incomplete.json` and the per-attempt lists in `regression.json`.

Non-reproducible failures observed (analogous to the documented R31, **recorded as open, not explained**):

1. **V2 attempt 2, `r32.test.ts` "multi-run shapes…"** failed once while four node crash reports were written in that attempt's window; the failure message was not captured at the time (the harness now records messages). It passed 6 of 6 times in isolation under the same environment and the full V2 **rerun was 118 / 118**.
2. **`computer.test.ts` "bounds completed audit storage…"** (a production test, unrelated to the rebuild) failed once with a 5.29 s duration (default 5 s timeout) in the first production run; 3 of 3 isolated reruns passed and the later production runs were clean.

A test-expectation bug was also found and fixed in my own tests: the W1 trace assertion hard-coded the incremental policy's last label (`cache:fallback_full`); under the full-rebuild policy the correct label is `cache:full` (it surfaced when the environment override first reached the child processes).
