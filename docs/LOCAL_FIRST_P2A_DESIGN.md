## 1. Executive summary

**Design verdict: P2a-0, P2a-8a, P2a-1, P2a-8b, P2a-2 and P2a-4 completed: PASS (scratch). GO to start P2a-5 (not started); later P2a steps remain governed by the sequence in section 12.** The original P2a-8 was replaced by P2a-8a (done) and P2a-8b (done, after the runner existed); P2b is on HOLD and re-scoped (P2b-0 / P2b-1). Nothing here changes the feasibility verdict (CONDITIONAL GO, L3).

1. **The runner contract is small and synchronous where it matters.** `AgentRunner` is four methods (`run`, `connect`, `isRunning`, `stop`). The local thread endpoints are synchronous (`listThreads()`, `getThreadMessages()`, … return plain values, not Promises), which fits `node:sqlite`'s `DatabaseSync` and OpenDots' existing storage. Confirmed.
2. **What is contract and what is detail.** Contract: events are replayed on `connect` and joined live if a run is active; a thread runs one run at a time; `stop` ends the run through the agent's `abortRun`; the persisted run input is sanitised against ids already seen; terminal events are guaranteed. Detail: the process-global store, LRU/`maxBytes` eviction, persisting only at finalise, `createdAt` taken at finalise. Confirmed (section 3).
3. **The runner, not the agent, persists the user message.** The user message lives inside the stored `RUN_STARTED.input.messages` that the runner attaches (`runtime:runner/in-memory.mjs:379`). A runner that persists only at finalise loses the user's turn on a crash. Confirmed.
4. **`reasoning.encrypted_content` never reaches the AG-UI event log.** Observed in P2a-8a (version-specific: CopilotKit 1.75.0, TanStack AI 0.63.0): the blob exists in the source fixture, then at `chat()`'s output as a **`REASONING_ENCRYPTED_VALUE`** chunk, and inside one `chat()` run it is re-sent to the provider as a `reasoning` item. **CopilotKit's `convertTanStackStream` does not forward that chunk**, so it is absent from every AG-UI event and from anything the runner can store. On the next run `convertInputToTanStackAI` forwards only user/assistant/tool messages, so **no reasoning item is sent across runs, today, in either mode**. Confirmed dynamically (P2a-8a, sections 5.1 and 5.5).
5. **Therefore the storage design splits into two concerns:** presentation history (the AG-UI event log; required) and model continuation (provider-specific, optional; not produced by the current pipeline). P2a must not assume the first can carry the second.
6. **Recommended source of truth:** an append-only **event-per-row log** as the single authority, with a per-thread **message snapshot as a rebuildable cache** (candidate B). A continuation table (candidate C) is reserved but not built unless a product decision requires cross-turn reasoning continuity. The final schema is **not fixed** here.
7. **Recommended write policy (candidate):** persist-then-publish at event boundaries (run start with its input, tool-call end and result, terminal event), buffered flushes for text deltas, one synchronous transaction per boundary, never across an `await`.
8. **Two findings that were not in the feasibility document** and affect the design: (a) `InMemoryAgentRunner`'s message-id set ignores `TOOL_CALL_START.parentMessageId`, so an assistant message that exists only through a tool call is not in its de-duplication set; a durable runner should add it to the **message** namespace and keep tool-call ids in a separate one (section 9); (b) replaying a past `RUN_ERROR` through `connect` very likely re-fires the chat's `onRunErrorEvent` and can show a stale error banner (section 8).
9. **What P2a-1 and P2a-8b observed** (scratch candidates, **not** approval of a production implementation; clean-run paths only). A scratch SQLite runner (event-per-row, W2) restarted across real processes and replayed exactly the G0 golden; it commits a synthetic `RUN_STARTED(input)` **before** the agent starts (section 7.6); its message cache is materialized eagerly at finalise because `getThreadMessages()` is synchronous while the public reducer is asynchronous (section 10.2); the `WorkspaceStore` connection seam is an open production-integration item (R16); and opaque `REASONING_ENCRYPTED_VALUE` strings (39 values, both subtypes, up to about 64 KiB) survive with exact string and UTF-16 equality (section 12.2). Crash recovery, stop, errors, HITL restart and performance were **not** evaluated by those two steps.
10. **What P2a-2 observed** (scratch candidates, **not** approval of a production implementation; single process per database). (a) The seen-message state is rebuilt from the **durable event history**, not process memory: three sequential turns store `[u1]`, `[u2]`, `[u3]` even though the real client sends its full history, across a process restart. (b) The message namespace (`RUN_STARTED.input.messages[].id`, event `messageId`, `TOOL_CALL_START.parentMessageId`) and the tool-call namespace (`toolCallId`) are independent; the G3 divergence (`[tool]` against the reference's `[assistant, tool]`) stays an explicit expected divergence. (c) The reference-derived `connect` that skips live events by message id is a **hazard**; the candidate gives the active run to the live subject only and never treats `messageId` as event identity. (d) The reference **accepts** a completed `runId` again; the candidate keys a run by `(threadId, runId)` and rejects duplicates fail-closed (reject versus reconnect for a retry is an open product/UX question). (e) One active run per thread, thread-local and **process-local**; multiple writer processes on one database are outside the current single-process target. (f) A crash-left `running` row is treated as an existing run but does not block the thread; recovery is P2a-4 / P2a-3. See section 12.3.
11. **What P2a-4 observed** (scratch candidates, **not** approval of a production implementation; single process per database; a **server** tool only). (a) After a real `SIGKILL`, a run is closed once, in one transaction, as `interrupted`; a server tool call with no recorded result gets an explicit "outcome unknown" `TOOL_CALL_RESULT` (not the stock `status: "error"`), then `RUN_ERROR(INCOMPLETE_STREAM)`. (b) A crash before the side effect (A) and after it (B) leave **conversation logs that the runner cannot tell apart**; only a test-only oracle shows the difference, so the generic runner claims only _interrupted / outcome unknown / verify before retrying_. (c) A durable result (C) is kept untouched. (d) **New risk:** the framework executes a tool call that has no result in the history it is given: with no recovery a new turn ran the tool again (attempts 1 to 2, receipts 1 to 2, a double side effect). A **provisional** scratch interlock (recover before a new run, refuse a stale input) stops it; it is not an accepted API or UX. (e) `client_tool_pending`, `tool_args_incomplete`, `open_text_message` and `no_tool_lifecycle` runs are **deferred** (P2a-5 / P2a-3), so R19 is **partially resolved**. See section 12.4.

### 2.2 Notes that change the design

- **`getThreadMessages` is synchronous**, so a synchronous store is a natural fit; an asynchronous store would need a cache. Confirmed.
- **The stored data is a replay source for the stock browser client**, which re-applies it with `defaultApplyEvents`. It must therefore stay valid AG-UI events. Confirmed.
- **The HTTP messages endpoint is not a fidelity channel.** OpenDots' own server-side consumers (voice context, save-to-page) call the runner directly, not HTTP. Confirmed.
- **`isRunning` has no SSE caller**, so its correctness is tested only by in-process users (P3) and by P2a itself. Confirmed.

### 5.2 What follows

1. **The AG-UI event log cannot carry the payload as the pipeline stands.** It never enters the log. Storing events faithfully (P2a's job) preserves what exists, which excludes the blob. Confirmed.
2. **Today there is no cross-run reasoning continuity, in Intelligence mode or SSE mode.** Both modes use the same converter; the runner sees only `DotAgent`'s AG-UI events. A local-first runner does not regress it. Confirmed.
3. **What a cross-run replay looks like today.** Observed (P2a-8a, Proof D): a second run on the same conversation sends `input` items `message:user, function_call, message:assistant, function_call_output, message:user` to the provider. There is **no `reasoning` item** and the blob is absent; the `function_call` item has only `type, call_id, name, arguments` (no item `id`, which `metadata.itemId` would have supplied but the AG-UI round trip drops). A call without an item `id` is a "fresh" item that the API is not asked to pair with a reasoning item (`responses-text.ts:2377`). Likely to be accepted by the API; **not verified live anywhere in this repository** (the Phase 6 real-account smoke covers a single run with a tool loop, not a second run). Unknown (P2b-0).
4. **Order caveat from P1-3, now confirmed dynamically.** Because the final text and the tool call share one assistant message, the provider input for a past turn lists the call, then the assistant text, then the call output: observed as `function_call → message:assistant → function_call_output` (P2a-8a, Proof D). Whether the provider accepts assistant text between a `function_call` and its output is **still Unknown and needs the live P2b-0**.
5. **AG-UI does have a standard slot.** `REASONING_ENCRYPTED_VALUE` (subtype `message` or `tool-call`, `entityId`, `encryptedValue`) exists in `@ag-ui/core` 0.0.59, `compactEvents` passes it through, and `defaultApplyEvents` writes it to `message.encryptedValue` / `toolCall.encryptedValue`. Nothing in this stack produces or consumes it (stage 7 and stage 10). Confirmed.

### 5.3 Does storage need two concerns?

| Concern                  | Content                                                                                                                                                                                                                                                                                             | Needed for P2a parity?                                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Presentation history** | AG-UI events and the messages derived from them. What the browser replays                                                                                                                                                                                                                           | **Yes**                                                         |
| **Model continuation**   | Provider-specific state needed to re-feed the model faithfully: for the Responses API, per thinking part `{reasoning id, summary text, opaque signature (version-specific; observed as a JSON string holding id + encrypted_content)}` and per tool call its `itemId`, in the original interleaving | **No** (not produced or consumed today). It is a new capability |

**Two routes exist if the owner later wants cross-turn reasoning continuity**; both are new work and neither is in scope for P2a:

- **Route 1, AG-UI native.** Capture the **`REASONING_ENCRYPTED_VALUE` chunk on `chat()`'s stream** (the most direct seam observed in P2a-8a; it sits on the public stream, so a wrapper around `chat()`'s output in `DotAgent`'s factory sees it before CopilotKit's converter drops it; TanStack's `middleware.onChunk`, the hook `run-error-code.ts` already uses, also sees chunks), emit it as an AG-UI `REASONING_ENCRYPTED_VALUE` event, and on the next run re-inject it as `thinking` parts in `DotAgent`'s factory because `convertInputToTanStackAI` drops it. The blob would travel through the browser (size, exposure to page JavaScript).
- **Route 2, server-side side table.** Store the continuation payload next to the run (candidate C) and re-inject it server-side. The browser never sees it. The AG-UI log stays pure presentation.

A third constraint applies to both: the collapse of a whole run into one assistant message (section 4, case 2) loses the interleaving the Responses API wants, so a faithful continuation would need TanStack's own message list for the run, not a reconstruction from AG-UI messages. Likely; Unknown how TanStack exposes it publicly.

## 7. Crash consistency (Investigation 6)

### 7.1 Constraints from the existing storage

- `Store` and `WorkspaceStore` each open a `DatabaseSync` on the same file with `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` and nothing else (`src/server/store.ts:29`, `src/server/workspace.ts:19`). Confirmed.
- Sub-stores that belong to a workspace share the `WorkspaceStore` connection (`new Pages(this.db, …)`, `new ComputerStore(this.db)`, `workspace.ts`). A conversation store should follow that pattern instead of opening a third connection. Confirmed (pattern); Likely (applicability). **P2a-1 shared the `WorkspaceStore` connection only by reading a private field in the scratch harness; production needs an explicit seam (R16).**
- `DatabaseSync` is synchronous. A transaction (`BEGIN … COMMIT`) opened and closed inside one synchronous stretch cannot interleave with other code on the same connection. **A transaction must never span an `await`.** Existing code already follows this (`Pages.update`, `createReviewed`, `Store.transaction`). Confirmed.
- Observed on Node 24.14.1 in a scratch database: SQLite **3.51.2**, `journal_mode=wal`, **`synchronous=2` (FULL)** by default, `wal_autocheckpoint=1000`, `fullfsync=0`. OpenDots sets none of them. Confirmed (read-only check).
- A committed WAL transaction survives `kill -9` of the process, because its frames are already in the operating system's file cache; `synchronous` only matters for operating-system or power loss. This is documented SQLite behavior, not measured here. **Likely; Requires PoC (P2a-3 with a real `kill -9`).**
- On macOS, `fullfsync=0` means an `fsync` does not force the drive's cache. Power-loss durability on macOS is therefore weaker than the name suggests unless `PRAGMA fullfsync` is set. Not a P2a concern (the target is process crash); recorded for P7. Likely.
- `synchronous=FULL` costs one `fsync` per commit. Per-delta commits at streaming rates would block the event loop for that long each time. The cost was not measured. Requires PoC (P2a-7).

### 7.4 Ordering rule: persist, then publish

For boundary events, write first and then push to live subscribers, so a client that sees `RUN_FINISHED` or a tool result can rely on it surviving a crash. The reference does the opposite (it publishes during the run and persists at the end). This is a deliberate difference to test (P2a-3, P2a-5). Likely.

### 7.5 Transaction boundaries (conceptual)

- **Run start:** one transaction inserts the run row (`status = running`) and the `RUN_STARTED` event with the sanitised input; it also registers the message ids seen. Committed before `agent.runAgent` is called (observed in P2a-1, section 7.6).
- **Boundary event:** one transaction appends the event and any buffered deltas ahead of it, preserving order.
- **Terminal event:** one transaction appends the terminal event, any closers, updates the run status, and refreshes the message snapshot.
- **Never** hold a transaction across the model call or any tool execution.

### 7.6 `RUN_STARTED` persistence strategy (observed in P2a-1)

An **observed candidate in the scratch runner, not approval of a production implementation.** The user's message exists durably only inside `RUN_STARTED.input.messages`, so the run start must be committed before model work.

- **Laziness.** `DotAgent.run` and `BuiltInAgent`'s run factory return lazy Observables: on subscription they emit `RUN_STARTED` and then proceed (asynchronously) to model work. The AG-UI client pipeline awaits each `onEvent` callback, but the source keeps running while the callback executes, so persisting the start inside a generic `onEvent` would **very probably** win the race against model work, but nothing guarantees the order.
- **Candidate.** `run()` builds a synthetic `RUN_STARTED` carrying the sanitised input, inserts the run row and event row 0 in one synchronous transaction, commits, and only then starts the agent.
- **No duplicate.** The agent's own bare `RUN_STARTED` (only `type`, `threadId`, `runId`) is not stored a second time. When it arrives, the runner attaches the persisted input to it and publishes it, so the published event is the durable one: exactly one `RUN_STARTED` row exists and the published stream carries exactly one.
- **Verified order.** Through a separate read-only connection, the run row and the `RUN_STARTED(input)` row (with the user message) were already committed when `DotAgent.run()` was called, when its Observable was subscribed, and when the fake provider received its first request.
- **Not exercised.** An agent that emits no `RUN_STARTED` (a startup failure): the code path exists, but no test ran it.

## 8. Restart recovery (Investigation 7)

### 8.1 State machine for a run row

| Status        | Meaning                                                                     | At boot             |
| ------------- | --------------------------------------------------------------------------- | ------------------- |
| `running`     | A run was in progress when the process died                                 | **Recover** (below) |
| `finished`    | Terminal `RUN_FINISHED` recorded, no stop                                   | Leave               |
| `stopped`     | Stopped by the owner; terminal `RUN_FINISHED` recorded with the stop marker | Leave               |

### 8.3 A stale-error risk found while reading the client

`Chat.tsx` subscribes to `onRunErrorEvent` before it calls `connectAgent`, and `connectAgent` applies replayed events through the same subscriber pipeline. A persisted `RUN_ERROR` in a thread's history would then very likely set the chat's error banner every time the thread is opened, **even when later runs succeeded**, because nothing clears the error as later events replay. This would be true in Intelligence mode too if it replays errored runs. Likely; Unknown whether Intelligence mode behaves this way; Requires PoC (P2a-6, at browser level). Options: keep errored runs' `RUN_ERROR` replayable and accept the banner; mark errored runs so `connect` replays them without the terminal error event; or clear the error on a later successful `RUN_STARTED` in the client. This is a UX decision, not a storage blocker. **Working default D3 (section 13):** historical `RUN_ERROR` events stay in the authoritative log, and the client must not keep presenting an old error as the current top-level banner merely because history was replayed; the exact client behavior is decided by P2a-6 after observation.

### 9.2 What prevents duplicates when the client resends history

The stock client resends the **whole** message list on every run. The runner drops the ones it has already recorded from the persisted `RUN_STARTED.input.messages`, while still handing the full list to the agent (the model needs it). Beyond that:

- **A re-sent user message** is filtered by `messageId`. P1-6 observed no duplicates on reconnect and later turns. Confirmed.
- **A re-sent run** with the same `runId` (a network retry of `POST /run`): the reference has no explicit rule; a concurrent one throws "already running", a finished one would create a second run with the same id. A durable store should enforce a **unique `(threadId, runId)`** and decide between rejecting and treating it as a reconnect. **Observed in P2a-2:** the reference **accepts** a completed `runId` again (a second run with the same id is recorded); the durable candidate rejects it fail-closed and rejects an active duplicate too, while the same textual `runId` on another thread is allowed. Reject versus reconnect for a retry stays an open product/UX question (section 12.3). Confirmed (P2a-2).
- **The client applies `RUN_STARTED.input.messages` by id** (it adds only messages not already present), so a message that appears in two runs' inputs is not duplicated in the browser. Confirmed (`agui-client` `defaultApplyEvents`).
- **The `parentMessageId` gap.** An assistant message that exists only through a tool call (HITL run 1) has no `TEXT_MESSAGE_*`, so its id is not in the reference's set. When the client re-sends it in the next run, it is **not sanitised out** of that run's stored input (the P1-4 protocol test re-sent it as the real client does, and the assistant message `9151…` is present in run 2's stored `RUN_STARTED.input.messages`). The browser dedupes by id on apply, so the visible effect is nil, but a durable id index and a messages snapshot built from stored inputs could duplicate it. A durable runner should add **`TOOL_CALL_START.parentMessageId` to its message-id set**. Confirmed (code and P1 protocol evidence); **P2a-2 confirmed the fix on the durable candidate** (the HITL resume stores `[tool]`; no duplicate message in the replay, the cache or the client; section 12.3); the effect across a HITL restart is still P2a-5.
- **Two namespaces, kept apart.** The **message** dedup set contains exactly: `RUN_STARTED.input.messages[].id`, event `messageId`, and `TOOL_CALL_START.parentMessageId`. **Tool-call ids are a separate namespace** (they identify a call, not a message) and are **never** used as `historicMessageIds` for sanitising `RUN_STARTED.input.messages`. A conceptual index keys both as `(threadId, kind, id)` with `kind = message` or `kind = tool_call`, so the two can never collide. Confirmed (the reference's set is message-only). **P2a-2 confirmed the separation by behaviour**: one string used as a message id and as a `toolCallId` did not collide, with no tool-call index and no new table. A tool-call index remains a design choice, Likely useful (for example to detect a re-sent tool result), Requires PoC.

### 9.3 Constraint candidates (conceptual, not DDL)

- Run: unique `(threadId, runId)`.
- Event: unique per-thread order key (an increasing integer is enough); index on `(threadId, runId)`.
- Seen ids: unique `(threadId, kind, id)`. `kind = message` covers input messages, event `messageId` (assistant text, tool-result messages) and `TOOL_CALL_START.parentMessageId`; `kind = tool_call` covers tool-call ids. Only `kind = message` feeds the sanitising of `RUN_STARTED.input.messages`.
- Foreign key from conversation rows to `thread_bindings(id)`, so ownership stays in one place.

- The event log is the only authority. The cache is derived from it with the public reducer and can always be rebuilt.
- `getThreadMessages()` is synchronous by contract, but the public `defaultApplyEvents` path is asynchronous (it also starts from `agent.messages`, not from `input.messages`, so the scratch derivation starts from an empty list). Rebuilding on the spot inside the synchronous endpoint is therefore not a fit.
- The scratch runner **materializes the cache eagerly at the terminal/finalise step** (after the terminal transaction, outside any transaction) and stores the id of the last event it covers as a staleness marker.
- At boot, `ready()` checks cache consistency and repairs a stale cache (a candidate seam; not a decision). A clean restart reported `checked: 1, rebuilt: 0` (P2a-1) and `checked: 2, rebuilt: 0` (P2a-8b), and reader-only boots wrote nothing.
- Outside an active run, a stale cache makes the scratch `getThreadMessages()` throw; whether a throw or a best-effort return is right is undecided.
- A new process derived the same messages from the events as the cache held, and the cache equalled the G0 golden messages.

### 12.1 Observed in P2a-1 (scratch; clean runs only)

- The G0 normal turn ran through the real client, the real `CopilotSseRuntime`, the scratch SQLite runner, the real `DotAgent` and the fake model. Process A exited; a different-PID process B opened the same database with a new runner. B's `connect` replay, `getThreadMessages`, `getThreadEvents`, `listThreads`, `getThreadState` and `isRunning` equalled the normalized G0 golden in **one strict whole-file comparison**. Nothing was normalized away and no fixture was edited. Process C repeated B: reader-only restarts performed **zero write transactions** and **zero provider requests**.
- Baseline candidate tables: `conversation_runs`, `conversation_events` (one row per event, whole event as `event_json`), `conversation_messages` (rebuildable cache). Not a final schema.
- Write policy W2: boundaries persisted then published; deltas buffered and flushed by a 250 ms timer or at the next boundary; no transaction spans an `await`; events stored uncompacted, compaction at read time.
- Findings carried into the design: sections 7.6 (`RUN_STARTED`), 10.2 (message cache) and R16 (connection seam).
- **Not evaluated:** `kill -9` recovery, stop, error and interrupted finalise, concurrent-run refusal, live join of `connect`, multi-run sanitising (the scratch runner adds `parentMessageId` to its message-id set, which diverges from the reference on purpose and is untested), HITL restart, dedup, and performance. A `running` row left by a crashed process is ignored today (recovery is P2a-3).

### 12.2 Observed in P2a-8b (scratch; a runner and persistence contract only)

- **Method.** A test-only synthetic agent emitted AG-UI events through `runner.run` (no direct INSERT). Writer A exited; reader B (new PID, same database, new runner, no model) and reader C (another new process) verified. 39 opaque values on two threads.
- **Subtypes.** Valid `REASONING_ENCRYPTED_VALUE` events of subtype `message` and of subtype `tool-call` were both preserved. The same textual id used for a message and for a tool call stays independent, because message and tool-call ids are separate namespaces.
- **Strings.** All 39 values (ASCII, Japanese, astral and emoji, combining sequences, backslash, quotes, LF, CR, tab, NUL, U+2028, U+2029, JSON-looking text, about 64 KiB, plus unpaired surrogates, an empty string and a mixed string) have **exact JS string equality** and **exact UTF-16 code-unit equality**. These are the authoritative criteria. No Unicode normalization or other transformation occurs anywhere.
- **UTF-8 is auxiliary.** `TextEncoder` byte equality was checked only for the 34 well-formed values. `TextEncoder` replaces an unpaired surrogate with U+FFFD, so for the other five a byte comparison could not prove code-unit fidelity. Nothing is claimed about SQLite's physical byte representation.
- **Events.** Unknown event fields were preserved, and the parsed `event_json` deep-equals the events the writer emitted. Replay through `connect` (direct and over the runtime's SSE) preserves the events and the opaque values. `compactEvents` may move an encrypted-value event relative to its entity's `END` (events that arrive while a message or tool call is open are attached after its `END`), but the event and its value remain intact.
- **Messages.** The direct runner `getThreadMessages()` preserves `encryptedValue` on messages (including the `reasoning` role) and on tool calls, as the public reducer sets it. The HTTP `/threads/:id/messages` projection **remains intentionally lossy** and was not changed. The HTTP `/threads/:id/events` endpoint preserves the event payload.
- **Restart.** Reader-only restarts performed zero write transactions, and readers B and C saw identical logical database contents. No provider request and no unexpected egress.
- **Negative controls.** Five deliberate mutations of the runner's serialization (NFC normalization, dropping an unknown field, truncating long strings, replacing raw U+2028, replacing unpaired surrogates) were each detected.
- **Scope of the claim.** P2a-8b is a runner contract only. The current ChatGPT-plan path **still does not generate this AG-UI event** (P2a-8a, version-specific). P2a-9 stays optional.

### 12.3 Observed in P2a-2 (scratch; clean runs, one process per database)

All sixteen PASS criteria held (see [`LOCAL_FIRST_P2A2_ACCEPTANCE.md`](LOCAL_FIRST_P2A2_ACCEPTANCE.md)); the golden fixtures are unchanged and eight deliberate mutations of the runner were each detected and reverted. These are **observed candidates, not approval of a production implementation**.

**De-duplication from the durable history.**

- Three sequential turns on one thread stored `RUN_STARTED.input.messages` of `[u1]`, `[u2]` and `[u3]`, although the real client sent its **full** history each time (`[u1, a1, u2]`, then `[u1, a1, u2, a2, u3]`). A process restart sat between turn 1 and turn 2: the second process had nothing in memory and its client history came from the durable replay. The seen-message state is therefore **rebuilt from the durable event history**, not from process memory.
- The implementation is a **history scan** (O(history) per run and per connect). No index table was added and the schema is unchanged. Whether an O(1) id index is needed is **not decided before P2a-7**.

**Namespaces.**

- **Message namespace:** `RUN_STARTED.input.messages[].id`, event `messageId`, `TOOL_CALL_START.parentMessageId`. **Tool-call namespace:** `toolCallId`. They are independent.
- HITL resume: the real client's request input is `[user, assistant, tool]`; the **reference stored `[assistant, tool]`**; the **durable candidate stored `[tool]`**. A fresh client replays the thread to the same four messages with unique ids.
- One string used as a message id and as a `toolCallId` did not collide (a new message whose id equals an earlier tool call id was kept; a tool message whose `toolCallId` equals a message id was kept).
- **The G3 difference remains an explicit expected divergence.** It is not hidden by a golden edit or by the normalizer.

**Reconnect: a correction to the reference-derived design.**

- P2a-1 had copied the reference's `connect`, which skips a live event when its `messageId` was already emitted from the historic replay. P2a-2 found that this can drop live events that are needed. **`TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT` and `TEXT_MESSAGE_END` share one `messageId` and are all required**, so **message-id based event de-duplication is rejected**.
- Candidate: the **active run is excluded from the historic read** and its events come **only from the live subject**, which replays that run from its first event; persisted history and live data are **exclusively owned per run**, and `messageId` is never used as event identity. The active run's rows are in the database as well (boundaries are persisted before they are published), which is exactly why the exclusion is needed.
- Observed: a late client receives the active run exactly once (`RUN_STARTED`, `TEXT_MESSAGE_START`, each delta, `TEXT_MESSAGE_END`, `RUN_FINISHED`), both when the deltas were only live and when every event was also persisted, and under a storm of connects at different positions; a connect after completion is history-only and read-only (no provider call, no write); a synthetic run that re-uses a historic `messageId` keeps all its events. A late joiner of an active run gets that run raw (per delta); after completion it is compacted, as in the reference.

**Duplicate `runId`: a new divergence from the reference.**

- **Reference (observed offline):** a completed `runId` reused on the same thread is **accepted** and a second run with the same id is recorded.
- **Durable candidate:** identity is `(threadId, runId)`; a completed duplicate is **rejected fail-closed**, an active duplicate is rejected, and the same textual `runId` on a **different thread is allowed**. Reasons: no overwrite of an existing run row, no events mixed into an old run, a unique durable identity. Rejection happens before anything is written and before the agent (the provider) starts, and the database is unchanged.
- **Open product/UX question, not decided:** a retry of a completed `runId` should be (1) **rejected**, or (2) **treated as a reconnect/replay of the existing completed run**. Today a retry gets an empty stream.
- **HTTP surface:** through the installed runtime both the reference and the candidate answer a rejected run with **HTTP 200, an empty `text/event-stream` and a server-side `console.error`**. This is the runtime's reaction to a synchronous throw and is **not fixed as the runner's production HTTP contract**. This divergence is not covered by a golden fixture.

**Concurrency.**

- Candidate semantics: one active run per thread; a second run on the same thread is **fail-closed**; a rejected run creates no run row, no events and no cache change, and never reaches the provider; **different threads run concurrently**; the lock is **thread-local, not global** (the same textual `runId` on two threads at once is fine).
- **Constraint, stated plainly:** the active-run exclusion is **process-local**. **Multiple processes writing the same database at the same time are outside the current single-process target of P2a** (R17). The durable key only protects against the same `runId`.

**Carried forward to P2a-4 and P2a-3.**

- A crash leaves a run row with `status = running`. The duplicate-run rule treats that `runId` as **existing**, but in the scratch behaviour the row alone does **not** block the thread (the active map is process-local). What recovery does with it is **decided in P2a-4 / P2a-3**, not by P2a-2 (R19).

**Update (P2a-4):** the server-tool part of this was settled by P2a-4 (section 12.4); R19 is only **partially** resolved.

**Also open:** how a rejection is shown to the owner (P2a-6 / P3, R8); duplicate detection was exercised for a finished run only (the rule applies to every status).

### 12.4 Observed in P2a-4 (scratch; a server tool under a real `SIGKILL`, one process per database)

All sixteen PASS criteria held (see [`LOCAL_FIRST_P2A4_ACCEPTANCE.md`](LOCAL_FIRST_P2A4_ACCEPTANCE.md)); the golden fixtures are unchanged, eight deliberate mutations of the runner were each detected and reverted, and the whole scratch suite is green. These are **observed candidates, not approval of a production implementation**.

**Method.** Real `SIGKILL`, sent by the orchestrator, at three **deterministic** gates (the tool waits until its own `TOOL_CALL_END` is durable; the orchestrator checks the database through a separate connection and then kills). A scratch agent wraps the real `BuiltInAgent` + TanStack + fake model with one extra server tool; `DotAgent` and the production tools are untouched. Separate processes: the writer (killed), a recovery process, a second recovery process, and a process that sends a new turn.

**Case A: `TOOL_CALL_END` durable, side effect not committed, `TOOL_CALL_RESULT` absent, process `SIGKILL`.** The oracle shows no receipt. **Case B: `TOOL_CALL_END` durable, side effect committed, `TOOL_CALL_RESULT` absent, process `SIGKILL`.** The oracle shows one receipt, visible from another connection before the kill. **The conversation logs of A and B are equivalent from the generic runner's point of view** (same events), while the test-only oracle differs (receipts 0 and 1). The recovery decision and the appended events were deep-equal. So **the generic runner cannot distinguish A from B, and must not claim anything beyond `interrupted`, `outcome unknown`, `verify before retrying`.** It does not assert success and it does not assert failure.

**Recovery event candidate.** For an ambiguous server tool call: a `TOOL_CALL_RESULT` with a **deterministic synthetic `messageId`** (`<toolCallId>-unknown-outcome`) and a **free-form string `content`** that says the outcome is unknown, the run was interrupted, and the effect must be verified before retrying; **no `status: "error"` and no `error` field**. Then `RUN_ERROR` with `code = "INCOMPLETE_STREAM"`, and the run row `status = interrupted`. The stock finalizer is used only for the structure (closers and terminal); **its synthetic failure result (`status: "error"`) is never persisted.** This is a **scratch representation candidate**: **not a new AG-UI protocol value** (AG-UI fixes only that `content` is a string) and **not production UX wording**.

**Case C: `TOOL_CALL_RESULT` already durable.** The result is **not changed** (byte-identical text), **no synthetic unknown result and no duplicate result is added**, only the missing terminal is added (`RUN_ERROR(INCOMPLETE_STREAM)`), the run is closed as `interrupted`, and the tool is not run again.

**Atomicity and idempotence.**

- The recovery events and the run status change are **one synchronous transaction**, which never spans an `await`. A fault injected midway rolled **everything** back; the next attempt applied the recovery once. (This test used a simulated abandonment, not a `SIGKILL`.)
- Whether recovery is needed is decided from **the database status** (`running`, and not run by this process), not from a process-local flag. A recovered run costs the next restart **0 write transactions**, and the logical database hash is unchanged.
- **Do not equate "one recovery transaction" with "one write for the whole boot".** The message-cache rebuild after the recovery is a **separate transaction**: the recovering boot used **2** write transactions (the recovery, then the cache rebuild); a later boot used 0.

**Side-effect oracle versus generic recovery.** The attempt table and the receipt table are **test-only**: they only let the test observe what really happened. **The generic recovery never reads them** (its source does not mention them; A and B, with opposite oracle states, recover identically). A **tool-specific reconciler** that keeps its own durable receipt could, in the future, look the effect up afterwards (observed: no receipt for A, one for B and C); **no such abstraction was designed in P2a-4.**

**New risk: the framework re-runs unresolved tool calls (R20).** With no recovery, a new turn on a thread whose history held an unresolved server tool call made TanStack **execute the call again**. Observed through the oracle: tool attempts **1 to 2**, and in Case B receipts **1 to 2**: **a double side effect really happened.** Safety requirement candidate: **unresolved server-tool history must not silently reach a new model/tool loop.** Recovery alone does not guarantee it, because the client sends the history it holds, which can be older than the log.

**Provisional scratch safety interlock (R21).** The scratch runner keeps two additions, for observation: **(1) pre-run recovery**: before a new run, the thread's recoverable dead run is closed; **(2) a stale-input refusal** (named `STALE_TOOL_HISTORY` in the scratch): when the durable log holds a tool result that the client's input lacks, the run is refused, **fail-closed**. Observed: **0 events written, 0 provider requests, 0 tool re-executions** for the refused run, and after a **reload** (the recovered history now contains the result) the same turn went through; a client (HITL) tool result, which is a tool **message** in the input and not a `TOOL_CALL_RESULT` event, is unaffected. **This is a provisional scratch safety interlock, not an accepted production API or UX**; the code name is **not** a production contract and must not be fixed.

**Server and client classification boundaries (R22).** The recovery is **server-tool only**. A tool call is a client tool when its name is among the `tools` in the persisted `RUN_STARTED.input`. P2a-4 **deferred** (left `running`, wrote nothing, not even an empty transaction, and did not block the thread) these four cases, and **did not accept** them:

| Deferred case          | Owner |
| ---------------------- | ----- |
| `client_tool_pending`  | P2a-5 |
| `tool_args_incomplete` | P2a-3 |
| `open_text_message`    | P2a-3 |
| `no_tool_lifecycle`    | P2a-3 |

The server-tool "outcome unknown" recovery is **not** applied to a client (HITL) tool call. These deferrals were tested with a simulated abandonment, which is **neither crash evidence nor HITL acceptance**.

**R19, partially resolved.** For the ambiguous **server-tool** case the sequence now holds: `running` row, restart, recoverable dead run detected, recovery transaction, `interrupted`, the thread continues. The general text, tool-arguments and client-tool cases are **not** resolved: R19 is **split across P2a-3 and P2a-5**, not closed.

## 13. Design recommendation

1. **Source of truth:** an append-only event-per-row log, authoritative; a per-thread message snapshot as a rebuildable cache; an id index if the scan proves costly (B with D). Not final.
2. **Keep presentation and continuation separate.** Do not try to make the AG-UI log carry reasoning. Reserve a continuation table (C) but do not build it for P2a.
3. **Write policy to test first:** W2 (boundaries persist-then-publish, deltas buffered), one synchronous transaction per boundary, shared `WorkspaceStore` connection (P2a-1 reached it through a private field in the scratch harness; an explicit injection seam is an open production-integration item, R16), no `await` inside a transaction.
4. **Recovery:** run the finalizer at boot on `running` runs, once, persisted; keep partial text; treat client-tool pending calls as pending. For server tools use the generic contract: no automatic re-execution, no success or failure assertion, recorded as `interrupted / outcome unknown; verify before retrying`; reconcile only where a tool has its own durable evidence. The terminal event for an ordinary interrupted run follows working default D2. **P2a-4 observed the server-tool part** (section 12.4) and added a safety requirement candidate: unresolved server-tool history must not silently reach a new model/tool loop (R20); the scratch interlock for it is provisional (R21).
5. **Dedup:** the message-id set contains `RUN_STARTED.input.messages[].id`, event `messageId` and `TOOL_CALL_START.parentMessageId`; tool-call ids live in a separate namespace and are never used to sanitise the message input (conceptual key `(threadId, kind, id)`); enforce unique `(threadId, runId)`. P2a-2 observed this on the scratch runner: the active run is owned by the live subject on reconnect (no message-id event filtering), a completed `runId` is rejected, and a retry policy is still open (section 12.3).
6. **Owner decisions, recorded as working design defaults** (design defaults for the PoCs, **not** approval of a production implementation):
   - **D1.** Current parity is sufficient. Cross-run reasoning continuation is **not** a P2a requirement. P2a-9 and the continuation table remain an optional new capability. P2b-1 is therefore not a core GO condition.
   - **D2.** For a genuinely interrupted ordinary run, prefer a truthful `RUN_ERROR(INCOMPLETE_STREAM)`-style terminal state. The pending client-HITL micro-window (client tool call ended, `RUN_FINISHED` not yet written) is a special case and must be tested in P2a-5 so that the pending decision is not destroyed.
   - **D3.** Historical `RUN_ERROR` events remain in the authoritative event log. They should not indefinitely present themselves as a current top-level error banner merely because history was replayed. The exact client behavior is decided by P2a-6 after observation.
7. **Dependencies on the rest of the feasibility work:** exact version pin and contract test for `ɵsupportsLocalThreadEndpoints` and the runner shape (C4/U6); P3 will call `runner.run` in-process and reuse the same runner.
